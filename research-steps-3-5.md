# Research: runbook steps 3–5 — framework, observability, schema (2026-08-19)

Grounded in Nous's official docs (hermes-agent.nousresearch.com), local inspection of `~/.hermes` on this Mac, and fetched-and-verified vendor/library docs. Every claim below traces to a source fetched today; local findings are marked as such.

## Step 3 — Framework: Hermes Desktop is sufficient on its own; run it headless

Hermes Desktop is the Electron front end over the MIT-licensed **Hermes Agent** runtime; desktop, CLI, and TUI share one backend, config, and session store [Hermes Docs: Desktop](https://hermes-agent.nousresearch.com/docs/user-guide/desktop). No second framework is needed:

- **Unattended execution is a first-class mode.** `approvals.mode` in config.yaml: `smart` (auxiliary LLM risk-assesses each action), `manual`, or `off` ("equivalent to YOLO mode"); YOLO also via `hermes --yolo`, `/yolo`, or `HERMES_YOLO_MODE=1`. Separate `cron_mode` / `single_query_mode` govern headless cron and one-shot runs. A hardline blocklist (fs wipes, fork bombs) always applies regardless of mode [Hermes Docs: Security](https://hermes-agent.nousresearch.com/docs/user-guide/security/).
- **Headless entry points:** `hermes serve` (backend gateway, no UI), `hermes send` (one-shot, aimed at "ops scripts, cron jobs, CI hooks"), `hermes -z` ("single prompt in, final response text out," `--usage-file` for machine-readable cost) [Hermes Docs: CLI Commands](https://hermes-agent.nousresearch.com/docs/reference/cli-commands).
- **Agent loop:** OpenAI-compatible message schema, tool-call loop with `max_turns` default 500 (sub-agents 50), concurrent tool calls via ThreadPoolExecutor [Hermes Docs: Agent Loop](https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop).
- **Tools:** ~84 built-ins incl. `web_search`, `web_extract` (clean page/PDF extraction), `terminal`, `process`, file ops, browser automation, sub-agent delegation, cron [Hermes Docs: Tools Reference](https://hermes-agent.nousresearch.com/docs/reference/tools-reference). **MCP is first-class**: `hermes mcp install`, `mcp_servers` in config.yaml, stdio + HTTP servers, per-server tool filtering [Hermes Docs: MCP](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp). **Native plugin system**: drop `plugin.yaml` + Python into `~/.hermes/plugins/`, register tools via `ctx.register_tool` [Hermes Docs: Plugins](https://hermes-agent.nousresearch.com/docs/user-guide/features/plugins).
- **Models:** DeepSeek (`DEEPSEEK_API_KEY`) and Kimi/Moonshot (`KIMI_API_KEY`) are named first-party providers; "any service with an OpenAI-compatible API works" via `provider: custom` + `base_url` [Hermes Docs: AI Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers). The client's model mandate is directly satisfied.
- **Profiles** isolate config/.env/SOUL.md/sessions/state.db per profile (`~/.hermes/profiles/<name>/`) but give NO filesystem sandboxing [Hermes Docs: Profiles](https://hermes-agent.nousresearch.com/docs/user-guide/profiles) — the stripped-toolset discipline in PLAN.md stays load-bearing.

**Fallback ranking if Hermes proves unreliable unattended** (client accepts equivalents): **LangGraph > Microsoft Agent Framework > CrewAI > OpenHands.**
- LangGraph: headless by default (interrupts opt-in), official MCP adapter, `thread_id` + SQLite/Postgres Checkpointer maps exactly onto claim→research→resume (re-invoke with same thread_id resumes from last checkpoint), deepest observability (OTel/LangSmith/Langfuse), MIT core, ~40k stars [LangChain persistence docs](https://docs.langchain.com/oss/python/langgraph/persistence). Caveat: checkpoints ≠ full durable execution mid-node.
- MS Agent Framework (AutoGen's successor; AutoGen itself is maintenance-mode since Oct 2025): `approval_mode="never_require"`, native OTel, workflow checkpoints + Durable Task extension; young (GA April 2026) [Microsoft Learn checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints).
- CrewAI: Flows + `@persist()` resumability, but no native DeepSeek provider (closed feature request) and open bug reports on custom base_url — integration risk on exactly our constraint.
- OpenHands: best DeepSeek/Kimi docs of the four and true headless always-approve mode, but no durable queue primitive at all — the whole claim/resume pattern would live outside it.

## Step 4 — Observability: capture is already built in; the gap is live viewing

**What Hermes already does (docs + verified locally on this machine):**
- `~/.hermes/state.db` (SQLite, WAL): `messages` table stores every turn with `role`, `content`, `tool_calls`, `tool_call_id`, `tool_name`, `timestamp`, `token_count`, `finish_reason`, `reasoning` — verified locally against the live schema; FTS5 indexes cover content + tool_calls; `session_model_usage` tracks tokens per session [Hermes Docs: Sessions](https://hermes-agent.nousresearch.com/docs/user-guide/sessions) + local `.schema messages`.
- `hermes sessions export --format trace` emits **Claude Code–compatible JSONL consumable by Hugging Face's Agent Trace Viewer**, secret-redacted, optional `--upload` to a private HF dataset; also JSONL/HTML/Markdown formats [Hermes Docs: Sessions](https://hermes-agent.nousresearch.com/docs/user-guide/sessions).
- `~/.hermes/logs/agent.log` — "all agent/tool/session activity," rotating, `RedactingFormatter` so secrets never hit disk (verified locally in `hermes-agent/hermes_logging.py`); `hermes logs -f --session --since` for filtering [Hermes Docs: CLI Commands](https://hermes-agent.nousresearch.com/docs/reference/cli-commands).
- **26 documented plugin lifecycle hooks** incl. `post_tool_call`, `post_llm_call`, `pre_api_request`/`post_api_request`, `on_session_start/end` — explicitly positioned for logging/auditing without touching core code [Hermes Docs: Plugins](https://hermes-agent.nousresearch.com/docs/user-guide/features/plugins).

**Gaps:** no live trace dashboard; transcripts are export-on-demand, not a realtime structured trace file; approval-decision audit trail is thin (only `hermes approvals suggest` mining state.db).

**Recommended layering (cheapest first):**
1. **Operator/run-level logging is application-level, not harness-level.** Per-company and per-datapoint outcomes (the thing the client's "logging that tells an operator what happened" requires) belong in queue.db/Postgres, written by the agent per AGENT-INSTRUCTIONS.md — do not conflate this with LLM tracing.
2. **Use the built-ins for harness tracing:** SQL over `state.db` during a run; `hermes sessions export --format trace` after runs for deep dives in the HF Agent Trace Viewer. Zero new infrastructure.
3. **If a live trace UI is wanted:** run **LiteLLM Proxy** (MIT; config-file-only for a single upstream) as the OpenAI-compatible endpoint Hermes points at, with the `arize_phoenix` callback → self-hosted **Arize Phoenix** (single Docker container, `arizephoenix/phoenix`, ELv2 source-available, zero feature gates). LiteLLM parses full request/response bodies (tool calls ride inside them) and forwards OTel spans with `gen_ai.*`/`llm.tools.*` attributes — no code inside Hermes [LiteLLM Phoenix integration](https://docs.litellm.ai/docs/observability/phoenix_integration). Langfuse is the heavier alternative (self-host needs Postgres + ClickHouse + Redis + S3) [Langfuse self-hosting](https://langfuse.com/self-hosting). Helicone is in maintenance mode post-acquisition — skip.
4. **Alternative to 3:** a small Hermes plugin on `post_tool_call`/`post_llm_call` streaming events to any sink — the hook system's documented purpose.

**Integration note (Agent Vault):** if LiteLLM runs, place it on the droplet next to the vault broker (or chain it behind the broker) so real model keys still live off-Mac; deciding the exact chaining order is an open two-way-door for the implementation session.

## Step 5 — Schema: one machine-readable catalog generates everything

Current mini hardcodes the 12 fields in three places (schema.json required-list, validate.py REQUIRED_FIELDS + per-field rules, catalog.md). At 200 fields that triplication is untenable. The researched pattern:

1. **`catalog.json` as single source of truth** — one row per field: `{field_name, type, enum_values?, collection_rule, description}`, plus top-level `catalog_version`. (catalog.md stays as the human view, generated or hand-synced from it.)
2. **Generate the JSON Schema (draft 2020-12)** from the catalog: one `$defs` envelope per value-type; one literal `properties.<field>` entry per row `$ref`-ing its envelope; status logic via `allOf` of `if {status: 'found'} then {required: [value, source_url], value: <type-schema>}` [json-schema.org conditionals](https://json-schema.org/understanding-json-schema/reference/conditionals); `unevaluatedProperties: false` (not `additionalProperties` — it can't see through `allOf`/`then`) to reject stale/unknown fields [json-schema.org object docs](https://json-schema.org/understanding-json-schema/reference/object). Stamp `catalog_version` into `$id` and validate it with `const`.
3. **Validator from the same catalog:** either `jsonschema` against the generated schema, or Pydantic v2 `create_model` with `__base__` carrying the shared `{status, source_url, note}` envelope and per-row value typing [Pydantic dynamic models](https://pydantic.dev/docs/validation/latest/concepts/models/). Replaces validate.py's hardcoded lists; keep validate.py's virtues — dependency-light, prints ALL violations at once, loud failures.
4. **Postgres storage: one JSONB result per company, NOT EAV.** `companies(company_id, catalog_version, result jsonb, updated_at)` with a GIN index (`jsonb_path_ops`) on `result`. Postgres's own guidance: prefer jsonb; a JSON document should be one atomic, together-updated datum (matches the write-once-per-company pattern; each update row-locks the whole row) [PostgreSQL JSON docs](https://www.postgresql.org/docs/current/datatype-json.html). EAV is the documented anti-pattern here; reserve it only if per-field audit history or per-field indexed range queries become real requirements.
5. **Versioning:** `catalog_version` lives in lockstep in three places — the catalog file, the generated schema's `$id`, and a typed SQL column (never buried in the JSON) — so results can be filtered/joined by the catalog that produced them.

Add/remove a field ⇒ edit one catalog row, regenerate; validator, schema, and storage all follow. Removed fields get retroactively rejected by `unevaluatedProperties: false` if the agent still emits them.
